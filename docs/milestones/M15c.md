# M15c: buildings, inner rings, performance pass, deploy

Goal: the city looks lived in, parks and lakes with holes draw correctly, the performance targets in plan §3.9 are measured and met, and the game deploys as a static site on GitHub Pages.

## Procedural buildings (`web/src/render/buildings/`)

Buildings are render-only and deterministic. They never reach the sim.

| File | Content |
|---|---|
| `rng.ts` | Pure: `mulberry32(seed)`, seeded by `(Math.imul(road, 2654435761) + side) >>> 0`, so each road side always produces the same buildings |
| `placement.ts` | Pure: `placeLots(road, side, store): Lot[]` (details below) |
| `kinds.ts` | Pure: `buildingKind(classCode, rand): 'house' \| 'commercial' \| 'warehouse'` (details below) |
| `draw.ts` | `drawBuildings(lots, graphics)` |
| `building-layer.ts` | Per-tile building graphics in `layers.buildings` |

**`buildingKind`:**

| Road class | Kind |
|---|---|
| `Residential`, `LivingStreet` | `house` |
| `Primary`, `Secondary`, `Trunk` | `commercial` |
| `Tertiary`, `Unclassified`, `Road` | `warehouse` 30 %, `house` otherwise |
| Anything else | Nothing |

**`placeLots`:**
- It runs only for roads with layer 0 and a length of at least 40 m, on both sides.
- Lots are placed along the road from 12 m after its start to 12 m before its end, every `12 + 6·rand` m.
- **Footprint:** the lot is oriented to the road tangent and set back 3 m from the road edge, which is half the road's width.

  | Kind | Width × depth |
  |---|---|
  | `house` | `(8 + 4·rand) × (8 + 6·rand)` m |
  | `commercial` | `(14 + 10·rand) × (12 + 6·rand)` m |
  | `warehouse` | `(18 + 10·rand) × (14 + 8·rand)` m |

- **A lot is skipped when:**
  - `pickRoad(p, 2)` hits an active road at any of its 4 corners or its centre. `pickRoad` already subtracts the half width.
  - It overlaps an earlier lot in the same tile. The test is an oriented-rectangle test over a small per-tile hash grid with 32 m cells, so lots from different roads at a block corner never overlap.
  - It is within 20 m of a node that has a junction ring.
- Commercial lots have a 30 % chance of a parking lot on their far side, sized `width × 10 m`.
- **Cap:** at most `MAX_BUILDINGS_PER_TILE = 600` per detail tile. Over the cap, keep every `k`-th lot in placement order, with `k = ceil(total / 600)`, so a dense tile thins evenly instead of stopping at an edge.

**Drawing** (plan §4):
- **Shadow:** first, a `#000000` alpha 0.16 copy offset by (0.8, 0.8) m.
- **Houses:** a `#8FD16A` rectangle, with a gable. The ridge runs along the long axis, and the half toward the down-right light direction is `#62A83E`.
- **Commercial:** `#4F7FD8`, with a 0.6 m lighter `#6E97E3` inset roof edge.
- **Warehouses:** `#5A5A5A`, with 3 thin `#4A4A4A` roof lines across the short axis.
- **Parking lots:** a white alpha 0.35 fill, with white stripes 0.12 m wide every 2.5 m.

**Layers and tiles:**
- `layers.ts` adds `buildings` after the tunnel layers (−3..−1) and before layer 0's containers.
- The container is visible only while `scale ≥ STREET_MIN_SCALE`.
- Buildings are built per detail tile, from the roads that the tile owns, inside the tile's existing build budget. They are destroyed with the tile.
- Placement anchors on every road, deleted ones included. Skipping only tests active roads.
  - So a deleted road keeps its houses, and a new road clears the buildings it overlaps once its tile rebuilds.
  - `invalidate` already dirties the tiles that own changed roads. It must also dirty every detail tile whose bounds intersect a changed road's bounds expanded by 40 m, because neighbouring tiles' lots can overlap the new road.

## Inner rings (mapgen and map format v4)

- **mapgen** assembles the inner rings of `type=multipolygon` relations, with members of role `inner`, using the same ring assembly as the outer rings.
  - An inner ring is kept only when its first vertex lies inside its outer ring.
  - Tiny inner rings follow the outer rings' simplify and minimum-area rules.
- **`AreaTable`** gains `hole: Vec<bool>`. A hole ring immediately follows its outer ring and has the outer ring's kind. `MAP_FORMAT_VERSION` becomes 4, and `validate` checks that no hole comes first or after a ring of a different kind.
- **Plumbing to the renderer:**
  - `AreaRender.hole: Vec<u8>` in `render/map.rs`
  - a `hole` getter on the wasm `AreaGeometry`
  - `AreaArrays.hole: Uint8Array` in the protocol, with its guard
  - the transfer in `worker/geometry.ts`
- **Renderer:** `drawAreas` draws each outer ring with `poly(points)`, then each following hole with `poly(hole).cut()`, then fills. Water is drawn before parks.
- **Fixtures:**
  - `MapBuilder::hole(points)` attaches a hole to the last `area` call. The builder's kind sort is stable, so a hole stays right after its outer ring.
  - `grid_city` gains a 30 × 30 m pond in the park's centre, as a park hole plus a `Water` ring for the same rectangle. The hole reveals the water.
  - Regenerate `web/public/maps/synthetic.bin.gz`. The grid's sim hashes do not depend on areas.
- The v3 and v4 bumps invalidate every save keyed by `map_hash`, and the real map once it exists. The orchestrator regenerates `metro-manila.bin.gz` with `build-map.sh` after each bump.

## Performance pass

**Carried from M7c:** the city step on `120x120@150` at 100k vph (about 23.9k active) is 14.7–15.2 ms median native, against the 12 ms target. The remaining cost is structural:
- occupancy sort, about 1.3 ms
- leader lookup, about 3.5 ms
- decisions, about 3.4 ms

Improve slot and network memory locality, for example by renumbering vehicle slots in occupancy order during compaction. Keep the golden-hash check from M7c for every pure change.

**Carried from M14:** vehicle kinds and lane changes raised the city median to 20.35 ms, with about 24.7k active vehicles.

| Cost | Time |
|---|---|
| Lane-change pass | about 3 ms |
| Serialization leader | about 1 ms |
| Exclusion pass | about 0.9 ms |
| Longer vehicles: more queueing, more active vehicles | the rest |

The targets stay: median ≤ 12 ms native.

**Carried from M10a:** deleting the busiest primary road at 100k vph on `120x120@150` gives a max step of 134.75 ms, against the ≤ 50 ms target.

| Cost | Time |
|---|---|
| Full route-graph rebuild | about 18 ms |
| City demand-table rebuild | about 12 ms |
| 73 immediate step-1 reroutes | about 44 ms |
| Refreshing every lookahead cache after the global version bump | the bulk of the remaining ~36 ms |

Apply M10a's two fallbacks, plus two more:
1. Patch only the changed nodes' CSR successor lists.
2. Reroute immediately only vehicles inside their decision zone, and flag the rest.
3. Update the demand tables incrementally for the changed links.
4. Key the lookahead cache on a per-node version, not the global one.

Measure first, then fix only what misses a target.

- **Native**, with `bench` on `120x120@150`:
  - the step median, p95 and max at 20k vehicles
  - mean A*
  - the max step for M10a's delete test
  - `--roundabout-at <tick>`: a radius-18 roundabout on the node with the most vehicles on its incident links (ties to the lowest id). Report the max step over the next 600 ticks, as for `--delete-road-at`.
  - `--add-road-at <tick>`: splits the most-used road at `length / 2` and connects it to the nearest node at least 30 m away that passes validation. Report the max step over the next 600 ticks.
- **Wasm:**
  - `grid120.bin.gz` is generated into `web/public/maps/` with `mapgen --synthetic 120x120@150` and gitignored, because the browser can only load maps from there.
  - A `bench.spec.ts` Playwright run (not part of `check.sh`, run it manually) loads `grid120` with `vph=100000` and reads the worker's step times from `stats` messages for 60 s after a 9,000-tick warm-up.
  - A region at 3k vehicles.
- **Render:** `?perf=1` makes the debug overlay record frame times (a 300-frame rolling p50 and p95, as `data-frame-p50` and `data-frame-p95`). Playwright reads them:
  - at city zoom (0.1 px/m) over the whole `grid120` map
  - at street zoom (10 px/m) over a dense block with 20k vehicles running
  - Swiftshader numbers are only relative. Also report them for a hardware-GPU run if one is available, or say that none was.
- **Load:** the time from page load to `ready`, and to the first frame with tiles, on `synthetic` and on `grid120`.
- For each target in plan §3.9 that is missed, report the profile's top 5 functions and a proposed fix. **Do not implement a fix without the orchestrator.** It will spec one.

## GitHub Pages deploy (`.github/workflows/pages.yml`)

- **Trigger:** runs on `workflow_dispatch` and on pushes to the default branch.
- **Steps:**
  1. Install the pinned toolchain the same way as `ci.yml`.
  2. Run `pnpm --dir web install --frozen-lockfile`.
  3. Run `scripts/build-wasm.sh`.
  4. Run `actions/configure-pages`.
  5. Run `pnpm --dir web build` with `TRAPIKS_BASE=/${{ github.event.repository.name }}/`.
  6. Upload `web/dist` with `actions/upload-pages-artifact`.
  7. Deploy with `actions/deploy-pages`, as step `id: deployment`.
- **Job settings:**
  - `environment: { name: github-pages, url: ${{ steps.deployment.outputs.page_url }} }`
  - `concurrency: { group: pages, cancel-in-progress: false }`
- **Permissions:** `pages: write`, `id-token: write`, `contents: read`.
- **`vite.config.ts`:** `base: process.env.TRAPIKS_BASE ?? '/'`.
- Every asset URL (maps, challenges, the worker and wasm) must already resolve against `document.baseURI` or `import.meta.url`. Fix any that do not. `challenges/<map>.json` is fetched through `new URL(…, document.baseURI)`.
- **`e2e/base-path.spec.ts`:**
  - `playwright.config.ts` gains a second `webServer` entry: `TRAPIKS_BASE=/trapiks-game/ vite build --outDir dist-base && vite preview --outDir dist-base --base /trapiks-game/ --port 4174 --strictPort`. So `check.sh` needs no extra step.
  - The spec checks that the title screen and a sandbox with vehicles load with no console errors.
- `README.md` gets a short "Play" and "Develop" section. It is the only doc the implementer may write, because it lives at the repo root, not under `docs/`.
