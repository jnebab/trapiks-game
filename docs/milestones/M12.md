# M12: challenges in sim-core (definitions, runs, scoring, replay)

Goal: `sim-core` can run a challenge deterministically:
1. a baseline on the untouched network
2. an evaluation that replays the player's command log at tick 0
3. a score with stars

Runs advance incrementally, so the worker can keep the UI alive and show progress. Screens and saves are M13.

This implements `docs/plan.md` §3.7. Every value below is fixed.

## Definitions (`src/challenge/def.rs`, ts-rs exported, serde)

```rust
pub enum Center { LatLon { lat: f64, lon: f64 }, Local { x: f64, y: f64 } }
pub struct Challenge {
    pub id: String, pub name: String, pub blurb: String,
    pub center: Center, pub radius_m: f64, pub seed: u64,
    pub vehicles_per_hour: f64, pub budget: i64,
    pub target_improvement: f64,
    pub star_steps: [f64; 2],
    pub min_throughput_ratio: f64,
}
```

- `target_improvement` is, for example, 0.25, meaning mean delay drops 25 %. `min_throughput_ratio` is 0.95.
- **Stars:**
  - 1 star when the challenge is passed.
  - 2 stars when `improvement ≥ target + star_steps[0]`.
  - 3 stars when `improvement ≥ target + star_steps[1]`.
- **Projection:** move mapgen's `Projection` into `sim-core` (`src/geo.rs`), using `libm::cos`, and have mapgen use it. Add `Projection::from_origin(GeoOrigin)`. `Challenge::center_xy(&MapData)` projects `LatLon` with the map origin, and returns `Local` unchanged.
- **Validation:**
  - `radius_m` must be 300–4,000, `vehicles_per_hour` 0 to `MAX_VPH`, and `budget` ≥ 0.
  - `0 < target_improvement < 1`, `star_steps[0] < star_steps[1]`, and `0 < min_throughput_ratio ≤ 1`.
  - Failures give a `ChallengeError`.
- A challenge that is not passed has 0 stars.
- **JSON shape:** `center` is externally tagged, for example `"center": { "Local": { "x": 1500, "y": 1500 } }`.

## Runs (`src/challenge/run.rs`)

```rust
pub struct RunResult { pub mean_delay_s: f64, pub throughput_per_hour: f64,
    pub created: u64, pub arrivals: u64, pub unserved: u64, pub stranded: u64 }
pub enum RunState { Running { done_ticks: u64, total_ticks: u64 }, Finished(RunResult) }
pub struct ChallengeRun { sim: Sim, warmup: u64, measure: u64, finished: Option<RunResult> }
```

- **`ChallengeRun::new(map, challenge, commands: &[EditCommand]) -> Result<ChallengeRun, EditError>`:**
  1. Builds `Sim::from_config` with `Region { center, radius }`, the challenge `seed`, its `vehicles_per_hour` and its `budget`.
  2. Enqueues every command.
  3. Calls `apply_queued()`, so the edits land at tick 0 before any vehicle exists.
  4. Drains `take_results()`. The first failed command returns its `EditError`.
  5. Sets `WARMUP_TICKS = 3000` and `MEASURE_TICKS = 6000`.
- **Frozen demand:** region mode freezes the demand tables at construction, per the M10a amendment.
- **Short runs for tests:** `#[cfg(feature = "fixtures")] ChallengeRun::with_ticks(map, challenge, commands, warmup, measure)` lets tests run 300/600 ticks.
- **`advance(&mut self, max_steps: u32) -> RunState`:**
  - Steps up to `max_steps`.
  - The checks run after every step: at `tick == warmup` it calls `reset_stats`.
  - At `tick == warmup + measure` it computes the `RunResult` from the stats window and returns `Finished`.
  - After finishing, further calls return the same `Finished`.
- **Metric**, over the measurement window:
  - `mean_delay_s = (accrued_delay_s + UNSERVED_DELAY × (unserved + stranded)) / max(1, created)`.
  - `UNSERVED_DELAY = 300.0`.
  - `throughput_per_hour` is as in M7b.
  - `accrued_delay_s` is measured against the frozen reference speed from M7b, and it includes spawn-queue waits.
  - With frozen demand tables, counting unserved and stranded trips means deleting access roads cannot game the score, and neither can lowering speed limits.

## Scoring (`src/challenge/score.rs`)

```rust
pub struct Score { pub improvement: f64, pub throughput_ratio: f64, pub cost: i64,
    pub passed: bool, pub stars: u8, pub reasons: Vec<FailReason> }
pub enum FailReason { NotEnoughImprovement, ThroughputDropped, OverBudget }
```

`score(challenge, baseline, after, cost)`:
- `improvement = 1 − after.mean_delay_s / baseline.mean_delay_s`. When the baseline delay is 0, the improvement is 0.
- `throughput_ratio = after / baseline`. When the baseline throughput is 0, the ratio is 1.
- `passed` requires all of:
  - `improvement ≥ target`
  - `throughput_ratio ≥ min_throughput_ratio`
  - `cost ≤ budget`
- `reasons` lists every failed condition, in the enum's order.
- `stars` follows the Definitions section.

## Command log (`Sim`)

- `Sim` records every enqueued command whose outcome was `Ok`, in application order, into `command_log: Vec<EditCommand>`, including `Undo`, which also succeeds.
- **Log compaction:** only the last `SetDemand` is kept. A new `SetDemand` replaces the previous one in place. `SetDemand` is never on the undo stack.
- On replay, the log's `SetDemand` wins over any separately saved demand value (M13's `vehiclesPerHour`).
- `Sim::command_log() -> &[EditCommand]`.
- Replaying the log at tick 0 on a fresh `Sim` gives the same `content_hash` as the live network. Validation never depends on vehicles, so every command succeeds again.

## Tests

1. **`score_rules`:** pass, each fail reason, stars at the boundaries, and a zero baseline.
2. **`challenge_files`:** both JSON files parse and validate. `center_xy` of `edsa-ortigas` on a `MapBuilder` map with origin (14.5995, 120.9842) is within 1 m of the hand-computed projection.
3. **`baseline_deterministic`:** two baselines of `downtown` on `grid_city(30×30 @ 150)`, using `with_ticks(300, 600)`, are equal field by field.
4. **`replay_matches_live`:**
   - The map is `grid_city(30×30 @ 150)` with the `downtown` challenge. The node for `SetJunctionControl { Signal }` must be unsignalized, or the edit is `NoChange`.
   - A live region `Sim` applies these edits at ticks 50, 400, 900, 1,300 and 2,000: `SetJunctionControl { Signal }` on a node, then `SetSignalTiming` on the same node, a flyover, a delete, and an `Undo`.
   - `ChallengeRun::with_ticks` with its `command_log` gives a `Sim` whose `content_hash`, road count, node count and road point ranges at tick 0 equal the live ones.
   - Two evaluations are equal.
5. **`flyover_improves`:** on `grid_city(10×10 @ 150)` as a `Local` challenge (centre (750, 750), radius 400, 3,000 vph), with `with_ticks(600, 1200)`: the baseline, then an evaluation with `BuildFlyover` at node (5, 5) over its two `Avenue 5` roads.
   - `after.mean_delay_s < baseline.mean_delay_s`.
   - Report both numbers, so the orchestrator can set a threshold.
   - If the assertion fails, report the numbers. Don't change the fixture or the edit to make it pass.
6. **`incremental_equals_bulk`:** with `with_ticks(300, 600)`, `advance(1)` repeated until finished, and a single `advance(u32::MAX)`, give identical results.
7. **`speed_limit_cut_does_not_improve`:** on the `downtown` region with `with_ticks(600, 1200)`, lowering every Primary road's limit to 30 km/h gives `improvement ≤ 0.02`.
8. **`deleting_access_roads_is_penalized`:** deleting the region's 3 highest-weight source roads gives a negative improvement.
